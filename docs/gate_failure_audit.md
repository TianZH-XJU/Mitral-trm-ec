# Gate 失败审计（任务 01，2026-10-26——只读现有轨迹与结果，无新训练）

## 核心结论：**无实现错误、无数据流缺陷——是真实的策略失败**，但根源是**类别失衡 + 信号信息量不足**，而非 Logistic Regression 优化方式不当。

## 1. `g2_train_n = 0` 之谜（R2 三个种子）

**确认原因：真实的类别极不平衡，非构造缺陷。**

R2 的 Gate1 oracle 标签分布（gate_train）：

| 配置 | oracle=0（e0 已对，应停） | oracle≥1（应继续） | 占比 |
|---|---|---|---|
| R2_s0 | 2,232 | 185 | 继续仅 **7.7%** |
| R2_s1 | 2,283 | 134 | **5.5%** |
| R2_s2 | 2,181 | 236 | **9.8%** |

组均衡逻辑回归在 6 维特征上学到的是**多数类基线**（"总停"）：训练内继续率 = OOF 继续率 = validation 继续率 = **0.000**（分类 acc 90–95% 完全由多数类贡献）。因此 Gate2 的训练集（= Gate1 OOF 判继续的样本）为空，`g2_train_n=0`。**OOF 交叉拟合本身实现正确**——空集是该策略在该特征空间上的真实行为，不是代码缺陷。

**重要的下游影响**：R2 的"gate"实际上是"永远停在 e0"策略（Gate2 从未训练也从未被调用）。因此 R2 的确认集结果（EM 91.8–92.9% vs 固定 e3 的 95.4–96.7%）就是 **固定 e0 基线** 的表现——R2 的 gate 实验等价于"e0 vs 最优固定深度"的比较，Gate2 的"省算但损准"解读在 R2 上不成立，需要修正为：**R2 的失败 = 总停在 e0**。

## 2. R1 的行为：几乎总继续（非"过度继续"——是 oracle 决定的）

R1 的 oracle 分布（gate_train）：oracle≥1 占 **92.5–96.6%**（e0 EM=0%，final-only 监督下 e0 几乎全错）。Gate1 学到"总继续"（继续率 99.8–100%），与多数类基线一致。**这不是 gate 误判——oracle 本身就该继续**。R1 的失败发生在 Gate2：总继续到 e3 的 N_cell（~920）高于固定 e3（~390）是因为**两阶段成本计算正确地包含了 e0+e1 两轮前缀生成**（协议规定成本全计），EM 却因 Gate2 在部分样本上停在 e1（错误层）而低于固定 e3。**成本核算与协议一致，无错**。

## 5. 判定（按审核的分支规则）

- **非**实现错误/数据流问题（无修复项）；
- **是**真实的策略失败，根源为：(a) 类别极度失衡（R2 继续 5–10%；R1 停止 3–7%），组均衡逻辑回归退化为多数类基线；(b) 信号跨种子不稳定（AUC 0.49–0.84）。
- **对 CMA-ES 的预判**（待任务 02 确认）：类别失衡是标签问题不是优化器问题——CMA-ES 若直接以 EM+成本为适应度（离散、非 oracle 标签），可绕开失衡标签问题，但**若特征本身信息量不足，优化器更换无法解决**（审核的"不要继续搜索同一组参数"分支风险）。任务 02 的信号增益分析是 CMA-ES 是否值得跑的决定性证据。
- R2 结果解读修正：其 gate 实验 = e0 固定基线（Gate2 从未被训练/调用），报告中已如实标注。

## 补充审计（2026-10-27）：轨迹生成存在 batch-level 特征/成本统计缺陷

**本节修正 §3 中“实现核对全部通过”的过宽结论。** OOF 按组划分和 oracle 标签定义的代码路径看起来合理，但这并不代表进入 Gate 的逐样本特征和成本统计正确。

### 发现

复核 `scripts/gate_gen_trajectories.py::decode_with_signals` 后，发现：

1. **`n_gen` 不是逐样本生成长度。** 它是控制整个 batch 解码循环的标量，每个循环步加一；写入 JSONL 时，同一个 batch 中所有样本都记录相同的 `n_gen`。因此保存的是该 batch 解码到全部样本结束所经历的循环次数，而不是每条预测实际生成的 token 数。后续 `fixed_apply`、`policy_apply` 直接使用此字段计算 `N_tokens` 与 `N_cell`，故逐样本成本及相关均值会被 batch 中其他样本的长度影响。

2. **置信度信号在样本结束后仍被累计。** `top1`、`margin`、`entropy` 和递归更新的 `dz` 在每一轮都先累计，而用于标记已结束样本的 `done` 并未用于屏蔽这些累计项。短序列在 EOS 后仍参与后续 batch 轮次的信号统计，最后再除以共享的 batch 级 `n_gen`。因此这些均值可能包含 EOS 后的无效步骤，并随同 batch 其他样本的长度变化。

3. **这会影响 Gate 的实际决策，而不只是日志。** `n_gen` 和这些信号都进入 Gate1/Gate2 特征，所以旧报告中的 OOF continue rate、`g2_train_n`、特征 AUC、Gate 动作以及策略成本，都不能作为“逐样本正确特征下 Gate 行为”的可靠证据。R2 的 oracle 继续标签比例很低这一观察来自预测 EM 转移，原则上不依赖该信号聚合缺陷，但应在修复后重新核对。当前不能断言 R2 的“总停”仅由类别失衡和特征信息不足造成。

4. **预测 EM 与 oracle 转移暂不直接判为失效，但需做批处理不变性抽查。** 代码在 EOS 后将输出 token 置为 PAD，因此预测序列及其 EM 看起来可能未被上述统计 bug 改变；不过应把一部分样本分别单独解码和混合 batch 解码，比较有效 EOS 前的预测是否一致，再保留相关 EM/转移结论。

5. **诊断脚本的可复现性不完整。** 当前提交的 `scripts/gate_signal_diag.py` 并未计算报告中列出的单信号 AUC，也未生成该 AUC 表；报告中的 AUC 应由可提交、可重复运行的脚本产生，不能只在文档里呈现数字。

### 对此前结果的处理

- 既有 Gate 确认集数据已经用于上一轮评估，**不得用旧 `gate_confirm` 选择或调试修复后的策略**。旧 Gate 确认结果保留为历史记录，但其信号和成本受上述缺陷影响，不作为有效的策略成本证据，也不能用来确认修复后策略成功。
- 固定深度的 EM/预测转移可能仍有效，但成本字段需从修复后的逐样本长度重新计算；在完成 batch-versus-singleton 抽查前，应标为待核验。
- 六个 base checkpoint 不需要重训；该修复属于推理轨迹与统计逻辑修复。

### 纠正后的后续顺序

1. 修复逐样本有效长度和信号累计：只对 EOS 前的有效解码步骤累计信号；记录每条样本自己的生成长度；确保已结束样本不再贡献置信度/熵/`dz`。
2. 增加测试：同一样本单独解码与混合 batch 解码的 EOS 前预测、信号、长度一致；手工复算若干样本的 `N_tokens`/`N_cell`。
3. **只重新生成并分析 `gate_train`、`gate_validation`** 的轨迹；不读入 `gate_confirm` 做策略选择，也不重训 base checkpoint。
4. 用可复现脚本重算 OOF Gate 动作、`g2_train_n`、AUC/适合类别失衡的指标、逐样本成本和 validation 策略表现。
5. 只有当修正后的候选信号在 group-level cross-validation 中显示可重复的判别增益，并在 validation 上得到一致的支持后，才重新评估是否批准 CMA-ES。当前仍不启动 CMA-ES。

本补充审计优先于本报告中任何基于旧轨迹信号、旧逐样本成本的结论。
